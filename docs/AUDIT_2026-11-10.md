# Audit 2026-11-10

What this repo does: harness-rag answers questions over U.S. Securities and Exchange Commission (SEC) filings that carry per-document read rules (access control lists (ACLs)). A FastAPI + LangGraph agent filters chunks in Structured Query Language (SQL), calls a model, checks the answer with a second model, and lets an admin approve one write tool (create_ticket). I judged it as a demo for a handful of users, but held it against the README's claim of a production shape (Fargate, Cognito, Verified Permissions, Bedrock, Temporal).

Checks I ran: `pytest tests -q` = 64 passed. `mypy` is clean. `ruff check` = 15 errors. I did not run the stack end to end or against AWS.

## Must fix

**1. Cognito login cannot work as built** (infra/terraform/modules/identity/main.tf:3-100, harness/identity.py:54-80, db/migrations/0002_seed_dev.sql)
- **What this is:** On Amazon Web Services (AWS), `verify_token` reads `sub` and `custom:org` from the Cognito identity (ID) token, then looks the user up in `principals` by `sub`.
- **Problem:** The pool defines no `custom:org` attribute, and the demo users are created with only an email. So `claims["org"]` is empty and every login fails with "token lacks sub/org" (401). Even with an org, `sub` is a UUID, while the only principals rows are the seed names `alice`, `bob`, `carol`. Nothing in the repo inserts principals or group_members for a Cognito user. The Cognito branch has no test.
- **Fix:** Add a `custom:org` attribute in Terraform (or take the org from config). Key principals on `cognito:username`, or write a post-confirmation step that inserts the principals/group_members rows. Add one test that decodes a fake Cognito-shaped token.
- **If we skip it:** The AWS deployment starts but nobody can sign in.

**2. The write-approval rule is enforced in one graph node, not at the tool door** (harness/runner.py:73-102, harness/tools/create_ticket.py:20-27, mcp_server/server.py:40-47, docs/SECURITY.md:4)
- **What this is:** `run_tool` is described as the one door. `ToolSpec.risk` says `write`, and `idempotent=False`.
- **Problem:** Nothing reads `spec.risk` or `spec.idempotent` (grep finds no use). Only the graph's `hitl` node asks a human. An admin using the Model Context Protocol (MCP) server calls `create_ticket` and it runs at once, with no approval. SECURITY.md says "no write runs without ... a human approval".
- **Fix:** In `run_tool`, refuse any tool whose risk is not `read` unless the caller passes `approved=True`. Only `hitl` passes it. Add a test that calls `run_tool` directly for carol and expects a refusal.
- **If we skip it:** Any admin can run write tools through MCP with no approval. The stated invariant is false.

**3. An approved write can be silently skipped, or run twice** (agent/graph.py:455, harness/runner.py:81-102, 543-549)
- **What this is:** The human in the loop (HITL) call uses idempotency key `"<thread_id>:create_ticket"`. `run_tool` checks the cache, runs the tool, then stores the result.
- **Problem:** The key ignores the arguments. A second approved ticket in the same thread (the user interface (UI) keeps one thread per conversation) hits the cache. It returns the first ticket's id and says "done", but nothing was created. In the other direction, two approve calls at once both see `snap.next`. Both resume, both miss the cache, and two tickets are created, because the check and the write are separate steps.
- **Fix:** Key on thread plus a hash of the arguments, plus the interrupt's checkpoint id. Claim the key first with `INSERT ... ON CONFLICT DO NOTHING` and run only if the insert won. Add a test with two approved tickets in one thread.
- **If we skip it:** A user is told a write happened when it did not, or it happens twice.

**4. Boot failure silently becomes a per-process memory checkpointer, and the health check always passes** (api/app.py:46-55 and 107-118, agent/graph.py:110-120 and 155, infra/terraform/modules/compute/main.tf:152, services/Dockerfile healthcheck)
- **What this is:** If Postgres is down at boot, `lifespan` logs and carries on. `_graph()` then compiles with `MemorySaver()` and caches it for the process lifetime. `/healthz` returns Hypertext Transfer Protocol (HTTP) 200 with `{"ok": false}`.
- **Problem:** The Application Load Balancer (ALB) matcher is `200`, and the Docker healthcheck only needs a 200. So a task with no database stays in rotation. Its threads and HITL state live in that one process. Approve on another task answers "nothing_pending". It never recovers when Postgres comes back.
- **Fix:** Return 503 from `/healthz` when `ok` is false. Make `_graph()` raise if the checkpointer was not set up, instead of falling back to `MemorySaver`. Keep the fallback only behind `configure(...)` in tests.
- **If we skip it:** One bad boot gives you a task that looks healthy but loses state and 500s on approvals.

**5. The ACL filter runs after the vector index, so restricted users get almost no dense results** (retrieval/sql.py:28-35, db/migrations/0001_schema.sql:69)
- **What this is:** The dense query orders by a Hierarchical Navigable Small World index (HNSW) and filters with the ACL `EXISTS`. pgvector applies that filter after scanning `hnsw.ef_search` (default 40) candidates.
- **Problem:** On the local database (DB), bob's readable set is 6 of 131 chunks (Form 8-K (current report) only). The 40 nearest chunks to a query are mostly Form 10-K (annual report), so the dense list for bob is usually empty or tiny. Only the keyword (sparse) path rescues him. I measured the counts but did not run the query.
- **Fix:** Run `SET hnsw.iterative_scan = relaxed_order` on each pooled connection (add it to `_configure` in db.py, pgvector 0.8+). Add a DB test where a user reads under 5% of chunks and still gets 24 dense rows.
- **If we skip it:** Users with narrow access get worse answers or "can't answer", and the README's item-level-ACL claim does not hold at scale.

## Should fix

**6. Approve runs the write with the principal frozen at request time** (agent/graph.py:430-466 and 543-549)
- **What this is:** `approve()` uses its `principal` only for the owner check. `hitl` then calls the tool as the principal saved in the checkpoint.
- **Problem:** If the admin role was removed after the request, the approved write still runs as admin. The Redis cache keeps roles up to 5 minutes anyway, but the checkpoint keeps them for as long as the thread waits.
- **Fix:** Resume with `Command(resume=..., update={"principal": principal.model_dump(mode="json")})`.
- **If we skip it:** A removed admin's pending write still executes after approval.

**7. A second turn on the same thread reuses the first turn's verification** (agent/graph.py:470-484, 331-334, 418)
- **What this is:** `_initial` resets most keys but not `verification`, `understood` or `policy`.
- **Problem:** On turn 2, `generate` reads `unsupported_claims` left from turn 1 and puts them in the system prompt ("drop them: ..."). An abstain on turn 2 also shows turn 1's verification. `approve` also resumes any thread with a pending node, including one that crashed in `generate`.
- **Fix:** Add `"verification": None, "understood": {}, "policy": {}` to `_initial`. In `approve`, check `snap.tasks` for an interrupt, not just `snap.next`.
- **If we skip it:** Wrong claims leak between questions, and approve can quietly re-run a failed turn.

**8. The query embedding model is never checked against the stored one** (retrieval/embed.py:79-91, ingest/writer.py:86-89, retrieval/sql.py:28)
- **What this is:** Each chunk stores `embedding_model`. Both backends produce 512 dims.
- **Problem:** Nothing compares them. If you ingest with fastembed and flip `HR_EMBED_BACKEND=bedrock`, the query vector is in a different space. The SQL accepts it and returns nearest-looking but meaningless rows.
- **Fix:** Add `AND c.embedding_model = %(model)s` to `DENSE_SQL`, passing `embedder.model_name`. Update the architecture test to match.
- **If we skip it:** A config change silently ruins retrieval quality, with no error.

**9. JSON Web Token (JWT) expiry is optional, and the defaults fail open** (harness/identity.py:69, config.py:9-12, api/app.py:121-128)
- **What this is:** In local mode `jwt.decode` is called without `require_exp`.
- **Problem:** I confirmed a token with no `exp` decodes fine and never expires. SECURITY.md says expiry is checked. The defaults are `hr_jwt_mode="local"` and secret `dev-only-change-me`. If an AWS task misses `HR_JWT_MODE=cognito`, `/auth/dev-token` mints admin tokens for anyone. Terraform sets it today.
- **Fix:** Pass `options={"require_exp": True}`. At boot, raise if `hr_mode != "local"` and (`hr_jwt_mode == "local"` or the secret is the default).
- **If we skip it:** One missing env var becomes an open admin door.

**10. Ingest parsing blocks the worker event loop** (ingest/workflow.py:119-125)
- **What this is:** `parse_and_write` is an `async def` activity that runs `parse.parse` and `parse.chunk` directly.
- **Problem:** BeautifulSoup plus lxml over a multi-MB 10-K takes seconds of central processing unit (CPU) on the loop. Other activities and the poller stall while it runs.
- **Fix:** `chunks = await asyncio.to_thread(lambda: parse.chunk(parse.parse(data, raw["content_type"])))`. The other blocking calls there already use `to_thread`.
- **If we skip it:** A busy worker looks hung and may time out other filings.

**11. Bedrock embedding fires one call per chunk with no cap and no retry** (retrieval/embed.py:79-82)
- **What this is:** `asyncio.gather` over `to_thread(self._one, t)` for every chunk of a filing.
- **Problem:** A 10-K has hundreds of chunks. Titan throttles, nothing backs off, and one throttled call fails the whole activity. Temporal then retries from scratch after 5 seconds.
- **Fix:** Limit with a semaphore of about 8 and build the client with `botocore.config.Config(retries={"mode": "adaptive"})`.
- **If we skip it:** Real ingestion on Bedrock keeps failing on large filings and burns retries (I did not run it on Bedrock).

**12. A model can ask for more facts calls than the turn budget allows** (agent/graph.py:281-293, config.py:44)
- **What this is:** `facts` loops entities x concepts, one tool call each. The budget is 8 tool calls.
- **Problem:** Bedrock's `understand` can return 3 tickers and 3 concepts = 9 calls plus the search. `charge` raises `BudgetExceeded` and the user gets an error event, not an answer.
- **Fix:** Cap the product at 6 (`itertools.islice`). Test with 4 entities and 3 concepts.
- **If we skip it:** Broad numeric questions fail outright on the real model.

**13. Continuous integration (CI) is red, and the riskiest code has no test** (.github/workflows/ci.yml, tests/)
- **What this is:** CI runs `ruff check .`. It currently fails on 15 findings in `evals/` (E501 line length, E741 `l`).
- **Problem:** No test covers `decode_claims`/`verify_token` (missing `exp`, wrong issuer, Cognito claims), any route in `api/app.py` (401, 403, dev-token 404 outside local mode), `writer.write` transaction behaviour (only the audit kind is tested), or the HITL cases in findings 2, 3 and 6.
- **Fix:** Fix or `noqa` the 15 lint errors. Add small tests for the cases listed, using FastAPI `TestClient` and the existing fake DB hooks.
- **If we skip it:** Pushes are blocked, and the fixes above could regress with no signal.

**14. `/chat` input is unbounded** (api/app.py:85-88)
- **What this is:** `question` and `thread_id` are plain `str` fields.
- **Problem:** A 5 megabyte (MB) question goes into the embedding call, the model prompt, the audit row and the checkpoint before the token budget can react. `thread_id` goes into the idempotency key and audit rows.
- **Fix:** `question: str = Field(min_length=1, max_length=2000)` and `thread_id: str | None = Field(None, max_length=64, pattern=r"^[\w-]+$")`.
- **If we skip it:** One user can run up model cost or fill the audit table.

**15. BedrockGateway keeps every call forever** (gateway/bedrock.py:33 and 70)
- **What this is:** `self.last_usage.append(usage)` on every `complete`.
- **Problem:** Nothing reads it (grep finds no other use). The gateway is one per process, so memory grows by 3 entries per chat for as long as the task lives.
- **Fix:** Delete the field and the append.
- **If we skip it:** A slow memory leak on long-lived tasks.

## Nice to have

**16. Dead code to delete** (ingest/parse.py:41-52, pyproject.toml, retrieval/sql.py:58-63, authz/entities.py:70-77, db/policies/documents.cedar:1-12, contracts.py:113, authz/audit.py:22)
- **What this is:** Code with no caller in the tree: `parse_pdf` plus the `pymupdf` dependency (Electronic Data Gathering, Analysis, and Retrieval system (EDGAR) primary docs here are HyperText Markup Language (HTML), and PyMuPDF is GNU Affero General Public License (AGPL) in a Massachusetts Institute of Technology (MIT) licensed repo); `DOCUMENT_READERS_SQL`; the Cedar `Document` resource path and `document_acl_read` policy (the runner and graph only ever ask about `Org`; the real read rule is the SQL predicate); `RiskLevel.money`; the `model.call` audit kind that is never written.
- **Problem:** Each line must be read and tested. The Cedar Document rule is a second copy of the SQL rule that nothing keeps in sync.
- **Fix:** Delete them. Move `langchain-aws` to the `evals` extra (only `evals/ragas_eval.py` imports it).
- **If we skip it:** A heavier image and a licence question, for no benefit.

**17. Migration lock is taken after the first write** (db.py:95-111)
- **What this is:** `run_migrations` runs `CREATE TABLE IF NOT EXISTS schema_migrations`, then takes the advisory lock.
- **Problem:** Two Fargate tasks booting together (the container command runs migrate on boot) can both hit the CREATE and one fails on a duplicate type error. Dev seed `0002` also runs in AWS and creates admin `carol` there.
- **Fix:** Take `pg_advisory_xact_lock` first. Keep the dev seed out of the migration path in `aws` mode.
- **If we skip it:** An occasional failed deploy, and dead admin rows in the prod DB.

**18. MCP principal never expires and `/documents` skips the role check** (mcp_server/server.py:61-66, api/app.py:163-165)
- **What this is:** MCP verifies `HR_TOKEN` once. `/documents` uses the ACL predicate but never asks Cedar.
- **Problem:** A long-running MCP process keeps the groups and roles from start-up after the token expires or access is revoked. A user with groups but no role is denied in chat, yet can list titles and uniform resource identifiers (URIs) of their documents.
- **Fix:** Re-verify the token on each tool call (the group cache keeps it cheap), and call `authorizer().decide(..., "retrieve", Org::...)` in `/documents`.
- **If we skip it:** Revoked access lingers in MCP, and the same rule gives two answers.

**19. The checkpointer uses one Postgres connection** (agent/graph.py:116)
- **What this is:** `AsyncPostgresSaver.from_conn_string` opens a single connection that every concurrent turn shares.
- **Problem:** Writes queue behind each other. If that connection drops (Amazon Relational Database Service (RDS) failover, idle kill), every chat fails until restart. I read this from the library's behaviour and did not reproduce it.
- **Fix:** Build the saver from an `AsyncConnectionPool` (`AsyncPostgresSaver(pool)`).
- **If we skip it:** Fine for a few users; one dropped connection takes the application programming interface (API) down.

## Left out
Seven smaller ones: `ping()` leaks nothing but opens a new connection per health check; `edgar._get` makes a new HTTP client per request; `hr_cors_origins` is not stripped after splitting; `DiscoverWorkflow` id has no run suffix; a filing marked `dead` has no way back; `idempotency_keys` rows never expire; the graph's numeric path never calls the calculator even though `retrieval/facts.py` says it does.

Verdict: Good bones (one SQL ACL predicate, fail-closed Cedar, real tests on the leak paths), but AWS login cannot work yet, and the write-approval and ACL-at-scale claims are not true in code today.

Lean: -60 lines, -1 dependency (pymupdf), 1 moved to evals (langchain-aws) possible.

Not checked: the React app (apps/web), Terraform beyond identity and compute, `evals/` datasets and scorers, architecture decision records (ADRs), the DB-backed tests (they may have been skipped here; the run printed 64 passed), live Bedrock/Cognito/Temporal behaviour, concurrency under load, the langgraph internals behind findings 3 and 19.
